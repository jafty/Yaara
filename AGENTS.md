# Working on Yaara

## Start on the deployment branch

- Unless the owner explicitly names another branch, all game development starts from `origin/codex/yaara-deployment`. `main` is not the current game-development baseline. Railway automatically deploys `codex/yaara-deployment`.
- Before analyzing game code or making edits, fetch that branch with `git fetch origin codex/yaara-deployment`, inspect the checkout and working-tree status, and switch to a local branch based on the fetched deployment branch. A differently named local branch is acceptable only after verifying that it includes the latest deployment commits.
- Every failed fetch must be explicitly reported with the requested branch, the failure reason, and the branch/commit actually available. A failed fetch must neither be ignored nor block continued work: try an available authorized alternative for reading the deployment branch, or continue with the best available local revision while clearly identifying it and limiting conclusions to that revision. Never imply that an unverified checkout represents the deployment branch or the running production version. Preserve the deployment branch as the intended baseline and retry synchronization before integrating or pushing changes.
- Preserve uncommitted work and existing deployment commits. Never reset, discard changes, or force-push to change branches. If local work prevents a safe switch, explain the conflict before proceeding.
- After switching, re-read that branch's `AGENTS.md` and the Markdown files it references. Follow those instructions for implementation and validation; do not use the instructions below from a stale `main` checkout as the development policy.
- After the full push checkpoint passes, commit and push completed changes to `origin/codex/yaara-deployment` by default. Fetch and integrate newer deployment commits before pushing. Do not create a pull request unless the owner explicitly requests one. Report the push result and Railway deployment verification separately.

## Project rules

- Read `docs/design-source.fr.md` for game rules and `docs/decisions.md` for explicit implementation choices. Do not silently rebalance existing games.
- Conversation and code (including identifiers, tests and comments) are English. Player-visible copy supports French and English through the checked-in Django catalogs. Preserve user-chosen names in either language.
- In-game screens are a plain, image-free manuscript: a single reading column, restrained typography, and scribe narration. House accounts use headings and prose; city summaries link to optional inspection folios, work decrees expose multi-city checklists directly on Decrees, and letters read chronologically. A player must never open cities one by one to repeat the same work; preserve one batch preview and seal for all selected cities. Native disclosures keep forms and reference material scannable without plus/minus styling. Keep exact costs and consequences clear. The pre-game interface can retain its conventional web layout.
- Work in the existing checkout. Cloud tasks are already isolated; do not create worktrees unless requested.
- The owner's 2026-10-19 usability revision supersedes the earlier navigation/map restrictions: three icon-and-label destinations (Council, Expeditions with crossed blades, Works), compact resources, and a public off-white schematic map. Keep the manuscript voice and realm-wide batch selection. Moon closure is provisional, not a navigation destination. New reigns use local city forges and a fifteen-road mesh; legacy saves retain realm equipment and their saved road network. See `docs/decisions.md` for scope and compatibility.
- The approved audit revision supersedes the initial mesh/economy defaults: new reigns use twelve-road frontier geography (`map_version=3`) and city-funded works/expeditions with 100/130/200 yield (`economy_version=2`). Existing saves retain their economy, roads, reservations and archived reports. New automatic reigns wait for explicit start; Railway cron resolves stored deadlines independently of browser activity. See the latest decisions and `docs/railway.md`.
- Keep the Python simulation independent of Django, storage, HTTP and clocks. Application services own authorization, per-game transactions, idempotency and persistence.
- Follow the established pseudo-TDD policy in `docs/testing.md`: define each logical use-case variation and its independent test before implementing it; use native Python stubs for external dependencies, or explicit inputs for pure functions. Preserve a one-to-one relationship between a specified variation and a logical test case. Parameterized rows count as separate cases; multiple assertions may verify one case.
- Run the entire existing suite, including real PostgreSQL integration tests and the browser smoke, for every push. CI must keep running all layers on pushes and PRs. A skip or a stubbed database is not evidence that a PostgreSQL requirement passed.
- New reigns use the version-two open-Moon calendar, beginning at Moon 1. Use `calendar.closing_moon` for tick targets and `calendar.closed_moon` for elapsed intervals. Saves without a calendar version retain their original timing. See `docs/decisions.md` before changing dates.
- Update both translation catalogs for copy changes and run `python scripts/compile_translations.py`. Keep narration independent of Django using structured `Message` values; translate only at the authorized presentation boundary. Do not rewrite original archived reports.
- Never send hidden opponent state or numerical combativity to the browser. Reports are immutable recipient-specific projections.
- Commands: `uv sync --frozen`, `uv run python manage.py migrate`, `uv run pytest --require-postgresql --fail-on-skip --check-case-catalog`, `uv run ruff check .`, `uv run python manage.py runserver`.
- Run PostgreSQL tests with `DATABASE_URL` pointing to a disposable database whose user can create test databases. Browser smoke: `uv run python scripts/browser_smoke.py` against a local running server.
- Keep HTML and CSS clean: no duplicate rules, dead styles, or appended override patches. Edit the owning component and its existing styles deliberately; reuse shared templates and components wherever practical. Remove obsolete markup and selectors together, and verify responsive, keyboard and no-JavaScript behavior when relevant. Maintain a clear heading/body type hierarchy and verify it with enlarged text as well as default sizes.
- Keep each change coherent and playable. No extra agent framework or distributed architecture is needed. Summarize behavior, checks, and remaining limitations after changes.
- Give each collected variation a stable `@case` ID and requirement; review updates to `tests/case_ids.txt`. Refactor only for a concrete benefit. See `docs/testing.md` for native stubs, report generation and the complete push checkpoint.

- Require 100% statement and branch coverage of all native core modules from logic cases alone: `uv run coverage run -m pytest -q -m logic --fail-on-skip --check-case-catalog`, then `uv run coverage report`. No coverage exemptions or database-backed logic cases. Specify behavior and side effects before implementation; artificial red-green baby steps are unnecessary.
